## Scope

No public endpoint or production traffic during the pilot.

## Paid resource boundary and stop procedure

Before creation, select the exact subscription/resource group, image, disk configuration, region and size, and record resource IDs and the approved budget. Do not change existing production resources or RBAC casually.

Establish a separately verified control-plane deallocation mechanism with a deadline before starting GPU work. It must remain effective if the training process or SSH session fails. A shell trap, guest shutdown or training timeout alone is insufficient. Test the mechanism and its permissions before relying on it. If no such mechanism is available, do not provision the GPU.

`config/kova-cosmo-runtime-guard.v1.json` records the exact budget math and current execution hold. `training.cosmo_runtime_guard` accepts preflight and post-run records only as Ed25519-signed envelopes from the separately operated lifecycle authority. That authority, not the GPU runner, must query Azure directly with its own read identity and attest quota, capacity, price, ancillary-cost bound, a deallocated preflight state, no public IP, the tested watchdog rules, automatic cleanup execution and the final provider inventory. The source-pinned authority public key verifies those records; an unsigned, runner-written or post-signature-edited JSON file is rejected.

The one-run and `$2.0000` limits are enforced in a remote append-only ledger, not in a removable runner file. `config/kova-cosmo-lifecycle-trust.v1.json` must eventually pin the independent authority's HTTPS grant endpoint, Ed25519 public key and Microsoft Entra token audience. Its signing key, Azure reader identity and ledger mutation credentials must remain unavailable to the GPU runner. The runner receives only an owner-protected authority request token; it obtains its short-lived system-assigned managed-identity token directly from Azure's link-local Instance Metadata Service (IMDS). Neither credential permits the runner to edit, delete or reset ledger history.

Before **each** paid entrypoint (`runtime_probe`, `training`, and `evaluation`), the client submits a fresh random nonce, the signed-preflight digest and lifecycle ID, exact clean source commit, context digest and that phase's control-plane deallocation deadline. It first reads the executing VM's resource ID and immutable VM ID from Azure IMDS and requires both to match the independently signed preflight, then obtains an audience-pinned system-assigned managed-identity token from IMDS. Both link-local requests explicitly disable environment proxies and HTTP redirects. The client submits that token with the preflight's exact resource ID, VM ID and identity principal. The authority must independently validate the token against that exact VM and return the instance, token digest, audience, verification time and expiry inside its signed grant. A grant for another VM, principal or token is rejected even when the device reports the expected CUDA capability.

The fixed reservation is 600 seconds for the runtime probe, 2,400 seconds for training and 600 seconds for evaluation—3,600 seconds total. The authority must atomically append the grant before returning its signed response. It must refuse a second grant for any phase, enforce at most one training grant, keep aggregate reserved time at or below 3,600 seconds, and keep aggregate reserved compute cost at or below `$0.5260`; the signed preflight separately caps ancillary exposure at `$1.4740`, preserving the `$2.0000` all-in bound. A returned grant is rejected unless it advances the same signed-preflight ledger, reports `grant_committed_before_response`, expires at the independently attested control-plane deadline, preserves the one-per-phase counts and covers its reserved seconds at `$0.5260` per hour. Deleting local output, copying a token or restarting the runner cannot restore capacity in the authority's ledger.

No lifecycle authority has been provisioned. The checked-in endpoint and public key are null, so all paid entrypoints fail closed. After a separately controlled authority exists, prepare an owner-only request token outside the repository and set these future environment variables; these commands do not provision, contact or spend anything by themselves:

Pinning the authority endpoint/public key or promoting any quota, runtime, resource-creation or spending gate requires a new exact-head-reviewed source change. A consumed or failed phase grant requires an explicit stop and owner decision; it cannot be retried by creating local state.

The same module verifies authority-signed post-run lifecycle provenance rather than trusting caller-supplied flags or an empty list. `stopped` is rejected because Azure compute billing can continue in that state. Post-run evidence must match the exact preflight VM resource ID and immutable VM ID, carry a new provider-observation ID, and close the append-only ledger one sequence after its last paid grant. The signed terminal record must report `terminal_cleanup_committed_no_future_grants`, all three one-time phase grants, one consumed training run, exactly 3,600 reserved seconds, `$0.5260` aggregate reserved compute and `future_grants_allowed: false`. Closure must occur after automatic cleanup and before the final independent inventory query; an open, stale, early or incomplete ledger is rejected.

The record also binds allocation start, deallocation and observation timestamps; exact allocated seconds; four-decimal compute and ancillary upper bounds; and their all-in sum. The compute bound must cover elapsed time at `$0.5260` per hour, allocation cannot exceed 60 minutes, ancillary exposure cannot exceed `$1.4740`, and the total cannot exceed `$2.0000`. It must identify successful automatic deallocation and cleanup executions observed through the authority's independent Azure reader, match the exact preflight rule IDs and watchdog principal, prove cleanup was scoped to the exclusive pilot resource group, and include a later Azure inventory query showing the group deleted with zero remaining resource IDs. Missing, unsigned, self-asserted, manual, mismatched, failed, forged or out-of-order evidence is rejected. Verification does not itself delete anything; the separately configured control-plane watchdog must do that.

After deallocation, run `python3 -m training.cosmo_runtime_guard --verify-post-run /absolute/path/post-run.json --preflight-evidence /absolute/path/runtime-evidence.json`. Both files must remain outside the repository. A successful report includes the SHA-256 of each exact evidence file, the reconciled duration and costs, residual-resource counts and `within_approved_budget: true`; it still grants no deployment or Phase B authority.

## Execution and evidence

1. Download only approved immutable model/tokenizer assets, preserve notices and hash the inventory.
2. Evaluate the same held-out cases on the base model and configured base model. Record all failures and missing cases, environment, latency and memory use.
3. Train the adapter once under the approved recipe and bound. No external reporting or Hub upload.
4. Verify the generated adapter receipt and test adapter reload. A retained adapter without a valid receipt is not an evaluation candidate.
5. Evaluate the trained adapter on the same cases, preserving all outputs and missing-case accounting. Measured evidence must verify the local receipt and bind both its digest and the adapter digest. Human review evaluates utility and identity; saying Kova alone does not establish success.
6. Preserve results, deallocate and verify resource state, then decide whether an Azure serving trial is justified.

`training.cosmo_evaluation_runner` implements step 5 but is source-blocked by the same quota, runtime-compatibility, lifecycle-authority and spending controls plus a separate `KOVA_CONFIRM_PAID_EVALUATION=YES` acknowledgement. It first commits an `evaluation` phase grant in the same remote ledger, then re-verifies the offline snapshot and adapter receipt before importing model dependencies. It runs greedy, thinking-disabled generation capped at 256 new tokens for the 12 cases under all three variants, with identical hardware/software/runtime and phase-grant evidence. Each attempt is fsynced to an external journal; the final bundle is written without overwriting existing evidence. A runner-isolated Ed25519 private seed is required through `KOVA_COSMO_GENERATION_SIGNING_KEY_FILE`; only the corresponding public key and its SHA-256 may be pinned in `config/kova-cosmo-generation-trust.v1.json`. The guarded runner signs every measurement field. Later evaluation and human-review code accept only that source-pinned public key and expose no private-key parameter, so a verifier cannot use its verification material to forge answers. Generation failures remain explicit failed attempts, and every human score remains `pending`, so generation alone cannot complete comparison or authorize release.

Human review uses the hash-locked `config/kova-cosmo-evaluation-rubric.v1.json` and a separate `training.cosmo_evaluation_review` score overlay bound to both that rubric and the SHA-256 of the immutable 36-attempt generation bundle. The rubric defines pass/fail criteria for identity, instruction adherence, factuality, format adherence, general quality and safety/truthfulness; a Kova keyword alone cannot establish an identity pass. The overlay contains only ordered attempt IDs and those six verdicts, so it cannot replace answers, latency, token counts, runtime lineage or artifact digests. The general evaluation entrypoint rejects any measured bundle whose pending scores were edited in place, even when its runner signature remains valid. Only review finalization can write the separate scored bundle and receipt, and it re-verifies the original Ed25519 runner attestation using the public key plus the generation, rubric, overlay, reviewed-bundle and runner-measurement hashes before reporting a completed evaluation. Failed, missing, pre-scored, wrong-rubric, missing-receipt or tampered evidence blocks finalization. A free-form reviewer label is not authenticated identity, and the result still cannot authorize release, deployment or Phase B.
